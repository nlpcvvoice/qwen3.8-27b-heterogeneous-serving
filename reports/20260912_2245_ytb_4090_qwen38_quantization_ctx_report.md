## 1. 为什么"那么快"——完整优化组合(非单一因素)

| 优化项 | 配置 | 效果(字幕实测数字) |
|---|---|---|
| 权重量化 | **UD-Q4_K_XL**(unsloth,Q4 系) | 默认配置即到 **45 tok/s** |
| ⭐ MTP 多 token 预测 | llama.cpp 一行参数开启 | cap 提到 70+/80+(coding)→ 长上下文回落到 6-70;**均值 ~70 tok/s** |
| ⭐ KV 缓存量化 | 降到 **Q4**(他实测不损质量,有人建议至少 Q8) | 让出显存 → 上下文从 128K 提到 **200K** |
| Thinking 档位 | 默认 high/X-high → 改 **low** | 「能少想就少想」;遇难题仍会多想 |
| max_tokens | 默认 ~8K → **20K → 32K**(防思考截断) | 20K 仍会被"想满",32K 够用 |
| Thinking 直接关 | llama.cpp 开关 | **90+ tok/s**(质量实打实损失) |
| 功耗 | 功耗墙限制 **80%** | 满载墙耗 520-530W |
| 模型能力结论 | 一周实测 | 可当**主模型**,感觉不出与 DeepSeek V4 Flash 差异(除速度) |

> 注意「那么快」= 组合拳:Q4_K_XL + MTP + (可选 KV Q4 开大上下文),缺一不可。

## 2. 上下文演化路径(重要)

| 阶段 | 上下文 | 结果 |
|---|---|---|
| 初始(未配置) | 32K | ❌ Agent 工作流不可用(一步塞 20-30K,两步就压缩,20 分钟任务被压崩) |
| 改配置 | **128K** | ✅ 11 分半、64 步完成 SSH+改 Hermes 任务,无压缩 |
| KV 量化 Q4 后 | **200K** | ✅ 实測能力不退化;「128K 还不是极限,我保守了」 |

→ 选硬件金句:「显存加载完模型之后,还能剩下多少留给上下文。上下文不够,再快也没用。」

## 3. 与我们项目的对照(2xT4 vs 4090)

| 维度 | 我们的 2xT4(48GB 总量) | 他的 4090(24GB) |
|---|---|---|
| 量化为 | Q4_K_M(UD) | **Q4_K_XL(UD)** — 更小的 4bit 粒度,更省显存更快 |
| MTP | 已开(`draft-mtp` n=2) | 已开(默认/一行参数) |
| KV cache | **q8_0** | **Q4**(他实测无差) |
| 上下文 | 96K | **200K**(靠 KV Q4) |
| 生成速度 | ~16 tok/s(96K,300tok) | **70+ tok/s**(均值) |
| 速度差主因 | T4 显存带宽 ~320GB/s,4090 ~1008GB/s(≈3.2×) + 单卡 24GB 无跨卡开销 | — |

### 对我们的启示(可行动项)

| 项 | 建议 | 收益 |
|---|---|---|
| KV 量化 | 把 `-ctk/-ctv` 从 `q8_0` 降到 `q4_0`,重新测 96K/128K/200K 上下文质量 | 上下文可开更大(他实测 200K 不退化) |
| 量化粒度 | 可对比 `UD-Q4_K_XL`(视频同款)vs 现 `Q4_K_M`,看 PPL/速度/显存三组差异 | 可能省显存+提速 |
| 并发预期 | 单 24GB 并发即跌到「三四十不到四十 tok/s」 | 校验我们 single-stream 策略正确 |
| thinking 档 | opencode/agent 场景可压 thinking=max_tokens 32K 防止「把速度全花在思考上」 | 长任务更稳 |

### 边界与注意

| 项 | 说明 |
|---|---|
| 硬件代差 | 4090 为消费卡,带宽/算力 ≫ 数据中心 T4;**数字不可直接迁移**,只取方法 |
| 他全程单流 | 并发速度崩塌 → 与我们 n_parallel=1(每槽全 96K)策略一致 |
| 「质量无损坏」 | 为其个人工作流主观结论;我们若改 KV Q4 需自己跑评测断言 |
| 费用对比 | 他算:比 API 省 ~一半,**~4000 元/年**(5 亿 token/月,含折旧;且 4090 不贬反涨) |
